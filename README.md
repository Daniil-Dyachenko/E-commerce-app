# E-Commerce-app

> Лабораторна робота №4: Helm Charts & Templating

---
## 1. Реорганізація інфраструктури (Структура Helm Chart):

Раніше всі наші ресурси лежали в папці k8s/ як звичайні текстові файли. Ми перенесли їх у спеціальну структуру Helm Chart.
Ми створили директорію ```charts/ecommerce-app/```, додали туди файл ```Chart.yaml```, який є ніби "паспортом" нашого застосунку, усі
старі маніфести ми перемістили в папку ```templates/```. 

---
## 2.Шаблонізація та параметризація (Values):

Ми позбулися жорстко заданих значень у файлі ```deployment.yaml```. 
Замість того, щоб щоразу вручну переписувати маніфест при зміні версії образу чи кількості реплік, ми винесли ці змінні у файл конфігурації ```values.yaml```.

```replicaCount```: Винесли кількість подів (за замовчуванням 2).

```image```: Винесли шлях до образу (ghcr.io/daniil-dyachenko/ecommerce-app), його тег (latest) та політику завантаження (pullPolicy).

```resources```: Додали блок обмеження ресурсів. Ми налаштували requests, тобто мінімум, щоб запуститись та limits, тобто максимум, який под може з'їсти, щоб не покласти весь кластер. 

У самому ```templates/deployment.yaml``` ми замінили статичні рядки на змінні Helm.

---
## 3. Управління різними середовищами (Environment Parity):

Ми створили додатковий файл ```values-prod.yaml```.У ньому ми вказали лише один параметр: ```replicaCount: 3```.Тепер, якщо ми розгортаємо застосунок для розробників, він займає 2 поди. 
А якщо ми застосовуємо прапорець ```-f values-prod.yaml```, Helm автоматично "перезаписує" базове значення і піднімає 3 поди для забезпечення більшої надійності на продакшені.

---
## 4.Automated Quality Gate(Автоматичне оцінювання):
Ми оновили наш GitHub Actions, додавши до нього lab4.yml, щоб він автоматично перевіряв наш Helm Chart при кожному пуші. Додали підняття KinD кластера. 
Це було необхідно, оскільки Helm потребує доступу до API Kubernetes навіть для симуляції розгортання.Скрипт перевіряє наш чарт на синтаксичні помилки та відповідність стандартам розробки.
Також скрипт перевіряє, чи дійсно кількість реплік змінилася на 3 і робить симуляцію встановлення чарта в кластер , таким чином гарантуючи, 
що Kubernetes прийме ці маніфести без помилок під час реального розгортання.
